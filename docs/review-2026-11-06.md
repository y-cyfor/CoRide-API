## 0. 结论速览

这个项目"能跑"，但**按当前代码直接部署到生产，存在多个必然触发的整站级故障**，其中两个与 2026-04 引入的"API Key 加密"和"渠道配额"直接相关。已修复的 131 项缺陷集中在 UI/CRUD/安全加固，**代理主链路（转发、计量、配额、限流、健康检查）反而没有系统性修复**。

| 级别 | 数量 | 说明 |
|------|------|------|
| P0 阻断 | 7 | 构建失败 / 上线 10 分钟全渠道下线 / 配额永久卡死 / 并发计数泄漏 / 协议不兼容 |
| P1 功能失效 | 15 | 权限、限流、多 Key 统计、模型映射、IP 白名单、统计口径等"有界面无效果" |
| P2 质量与运维 | 11 | WAL、超时、日志、CORS、迁移兼容性等 |

另外，**当前工作区前端有语法错误，`pnpm typecheck` 与 `pnpm build` 都会失败**；HEAD 是好的。这一点直接决定 CI 的 Docker 构建能否通过。

## 2. P0：阻断级缺陷

### P0-1 工作区前端语法错误，构建必失败

- **证据**：`pnpm typecheck` 输出 `src/views/routing/traffic-plan/index.vue(325,1): error TS1128: Declaration or statement expected.`
- **根因**：删除"权重和必须为 100%"校验时，只删了 `if (...) {` 和 `return;`，留下了配对的 `}`。`web/src/views/routing/traffic-plan/index.vue:288-299` 多出一个闭合括号，函数在第 298 行提前结束。
- **影响**：`vite build` 同样会失败 → 一旦把当前工作区提交并推送，Docker 前端阶段必然失败，`.github/workflows/docker.yml` 会红。HEAD 版本没有此问题，是未提交改动引入的。
- **修复**：删除 `web/src/views/routing/traffic-plan/index.vue` 第 298 行多余的 `}`。

### P0-2 健康检查把密文当 API Key，约 10 分钟后自动禁用全部渠道，且永不自愈

- **触发链**：
  1. v0.4.4 起渠道 Key 默认 AES-GCM 加密入库：`models.rs:304`（create）、`models.rs:345`（update）。
  2. 健康检查后台任务启动即跑、每 5 分钟一次：`main.rs:214-218`。
  3. `health.rs:21-22` 直接 `SELECT api_keys`，**没有解密**；`health.rs:42` 取 `keys[0]` 当 Bearer/x-api-key。
  4. 上游收到的是 base64 密文 → 401 → `consecutive_failures + 1`：`health.rs:91-114`。
  5. 第 3 次（约 10 分钟）→ `status = 'disabled'`：`health.rs:94-104`。
  6. 之后 `find_channels_for_model` 只查 `status = 'active'`：`models.rs:455` → 返回 404 "Model not found or no active channels"。
  7. 恢复分支只遍历 `status='active'` 的渠道：`health.rs:20-22`、`68-80` → 被自动禁用的渠道**永远不会再被探测**。
- **影响**：任何新建或编辑过渠道的实例，部署约 10 分钟后全站代理不可用；管理员手动重新启用后，再过 10 分钟再次全灭。这解释了"渠道测试通过但实际不能用"的体感。
- **修复**：`check_channels_health` 接收 `encryption_key` 并调用 `models::maybe_decrypt_api_keys`；`/models` 返回 404/405 时视为"不支持探测"而不是失败；区分 401（Key 问题，告警）与网络错误；自动禁用的渠道也要参与探测（或加 `auto_disabled` 标记 + 指数退避重试）；给健康检查加开关。

### P0-3 渠道配额永不复位，且 requests 类型按 token 扣 → 配额耗尽后永久 402

- **证据**：
  - `create_channel` 的 INSERT 列里没有 `quota_period_start/quota_period_end`：`models.rs:306` → 周期结束时间恒为 `NULL`。
  - `reset_channel_quota_if_expired` 只在 `Some(end)` 时重置：`quota.rs:117-141`；`NULL` 直接跳过。
  - `deduct_channel_quota` 不区分 `quota_type`，永远按 token 加：`quota.rs:147-153`、`models.rs:628-642`。
- **触发场景**：渠道配置 `quota_type=requests, quota_limit=1000, cycle=daily`。两次请求各消耗约 800 token 后 `quota_used≈1600 > 1000`，第三次起 `check_channel_quota` 返回 402（`proxy_routes.rs:191-194`），且**第二天也不会恢复**，只能手动改库。
- **影响**：这是最典型的"流程阻塞"——单个渠道配额耗尽会挡死所有依赖它的用户，且没有自愈路径。
- **修复**：创建/更新渠道时按 `quota_cycle` 写入周期；`deduct_channel_quota` 按 `quota_type` 分别加 1 或加 token；`reset_channel_quota_if_expired` 在 `period_end IS NULL` 时以创建时间为起点补初始化。

### P0-4 全局并发计数器泄漏 + 流式提前释放 → 要么失效，要么永久 429

- **证据**：`rate_limit.rs:64-88`。计数器是进程级 `AtomicU32`，递增后必须执行到 `fetch_sub` 才释放。
- **泄漏路径**：客户端在等待上游时断开/取消（Claude Code 按 ESC、关闭窗口、网络切换），`next.run(request).await` 被 drop，`fetch_sub` 永远不会执行；handler panic 同理。累积到 `concurrency`（默认 50）后，**所有代理请求永久返回 429 "Too many concurrent requests"，只能重启进程**。
- **失效路径**：对流式响应，handler 返回响应头后 `next.run` 就结束了，计数器立刻减 1，实际上并没有覆盖整个流式生命周期。也就是说"并发限流"对最需要限流的流式请求完全不生效。
- **修复**：用 RAII guard（`Drop` 里递减）；流式响应把 guard 绑到 body stream 的生命周期上（或用 `tower::limit::ConcurrencyLimitLayer` + body 包装）。同时区分"连接被取消"和"请求失败"的日志。

### P0-5 代理错误一律返回 HTTP 200；非流式成功响应被包进 `{code,data}`

- **证据**：
  - `proxy_routes.rs:360-366`：`error_response` 只 `Json(...)`，不带状态码 → 401/402/404/429/502 全部以 **HTTP 200** 返回。
  - `proxy_routes.rs:329-334`：非流式 2xx 被包成 `{"code":0,"data":<上游响应>}`。
- **影响**：
  - OpenAI SDK 看到 200 就按 `choices` 解析，拿到的是 `code/data`，直接抛解析异常；而且不会触发 SDK 的 429/5xx 自动重试与退避。
  - 配额超限、模型不存在、渠道全挂这些"应该让客户端停下来"的状态，客户端完全感知不到。
  - 与 README "OpenAI / Anthropic 兼容接口"的定位直接冲突。
- **修复**：`error_response` 改为 `(status, Json(...))`；非流式响应原样透传上游 body（若内部测试确实需要包装，用独立字段或 query 开关）；错误体按协议返回 `{"error":{"message":...}}`（OpenAI）或 `{"type":"error","error":{...}}`（Anthropic）。

### P0-6 流式路径不判断上游状态、不跨渠道重试、失败也扣费

- **证据**：`proxy_routes.rs:234-279`、`proxy.rs:206-255`。
  - `proxy_request_stream` 不检查 `resp.status()`，直接 `Ok(Response)`。
  - 于是上游 401/429/500 都被当作成功：扣用户/渠道配额（`:249-250`），日志记 `status_code=200`（`:258-272`）。
  - `Ok(resp) => return resp` 直接返回，**不会尝试下一个渠道**。
- **影响**：
  - 多渠道路由在主路径（流式）上退化成"只用权重最高的那个渠道"；一个 Key 失效、被限流、余额不足，用户立刻全挂，其他渠道形同虚设。
  - 失败请求照扣配额；日志/统计把失败记成成功。
  - 2026 年主流客户端（Claude Code / Codex CLI / Cline）默认全是流式，所以这不是边角场景，而是主场景。
- **修复**：先判断 `status.is_success()`；非 2xx 读一小段 body 后走 `last_error` 并切换渠道；只有真正开始流式输出（2xx）才扣费；在流结束回调里记录真实状态、耗时与 usage。

### P0-7 没有上游超时，挂起的请求会占满并发

- **证据**：`proxy.rs:68-76` 构建 `reqwest::Client` 时没有任何 timeout；配置里的 `proxy.timeout`（`config.rs:50`）和 `channels.timeout`（`models.rs:45`）**全项目没有任何地方使用**（全仓 grep 只在设置页展示和健康检查 10s 出现）。
- **影响**：上游不响应时请求无限等待，占住 `channel_semaphores` permit 和全局并发计数。与 P0-4 叠加，几十个挂起请求就能把服务拖死。
- **修复**：用 `channel.timeout`（毫秒，默认 300000）设置 total timeout，另加 connect timeout；流式请求用"首字节超时 + 空闲分片超时"而不是总时长；`pool_idle_timeout` 一并设置。

- **`error_response` 在 admin 侧同样返回 200**（`admin_routes.rs:191-196`）：前端靠 `code` 字段能用，但脚本/监控/网关无法按 HTTP 状态判断失败。

## 4. P2：质量与运维

1. `list_users` 把不同配额的 `total_limit` 直接求和（requests 和 tokens 相加），展示值无意义：`admin_routes.rs:364-376`。
2. 配额没有 `(user_id, channel_id)` 唯一约束，可创建重复配额，实际取最新一条：`models.rs:584-608`。
3. `get_user_quota_for_channel` 的"渠道配额优先"是**覆盖**而非**叠加**，用户总配额在存在渠道配额时被绕过：`models.rs:589-608`。
4. 管理端日志不支持按用户筛选（`None` 硬编码）：`admin_routes.rs:981-988`。
5. 日志表存的是**完整 API Key 明文**（`request_logs.user_api_key`），CSV 导出才脱敏；多 Key 场景下还会把"同一用户"拆成多条统计线。
6. `active_users` 统计的是不同 Key 数，不是用户数：`admin_routes.rs:920-925`。
7. 登录限流的 `DashMap` 按 IP 无上限增长（`rate_limit.rs:107-115`），可被扫描器撑大内存。
8. `refresh_token` 就是一个 7 天有效期的普通 access token，无类型区分、无轮换、无吊销（`jwt.rs`、`admin_routes.rs:251-260`）。
9. 缺少端点：`/v1/responses`、`/v1/embeddings`、`/v1/messages/count_tokens`；Claude Code 的 count_tokens 与 Codex 类客户端会直接命中 404。
10. 查询串被丢弃：`handle_proxy` 只传 `path`，`?beta=true`、`?alt=sse` 等参数不会转发（`proxy_routes.rs:35`、`proxy.rs:161`）。
11. 无任何后端集成测试与 CI 测试：全仓只有 `token_counter.rs` 的 4 个单测；`vibe/test` 依赖真实上游 Key 的 Playwright 脚本，不可在 CI 复现。这让上面每一条修复都无法自动回归。

## 5. 2026-11 视角：还有没有必要继续维护？

### 5.1 结论

**不建议继续做"功能开发"；建议二选一：**

- **A. 维护模式（推荐，如果你还在用）**：只修 P0/P1 + 依赖升级，冻结新功能。投入约 **3-5 人日**，之后每季度半天巡检。
- **B. 停维归档（如果你已经不用老 coding plan）**：保留 Docker 镜像自用，代码归档。理由见下。

只有在一种情况下值得升级为 **C. 转型为"团队 token 网关"**：你们确实需要"一个入口 + 多厂商故障切换 + 按人/按 Key 预算"，并且愿意再投入 **2-4 周**补齐计量与兼容性。否则不如直接用厂商的 team/org token plan，或 LiteLLM / new-api。

### 5.2 为什么"拼车"的价值主张消失了

原项目的核心收益来自**"按次/包月套餐"的套利**：一份固定月费（例如若干小时/若干次请求）由 N 人分摊，用配额和时段分流把"次数"切成份，再用 UA/请求头伪装成不同客户端规避风控。

按 token 计费后，这套逻辑有三处失效：

1. **成本不再固定**：总成本 = 总 token × 单价，拼车不产生规模套利，只产生"分摊"。省下的只是"每人最低消费"和"可能的批量折扣"。
2. **风险收益反转**：共享账号、伪装客户端在厂商 ToS 下依然是高风险行为；而厂商现在普遍提供 team plan + 子 Key + 用量看板 + 预算，合规路径已经存在。
3. **本项目的差异化（伪装、分时段流量方案）在 token 时代几乎无收益**，反而增加了维护面和合规风险。

而 token 时代真正有价值的能力——**精确计量、成本核算、预算控制、多厂商路由/故障切换、协议兼容**——恰好是这个项目最弱的部分：流式不计 completion、模型映射不生效、配额不复位、限流不生效。也就是说，它现在既没有"拼车"的套利，也没有"网关"的基本功。

### 5.3 决策矩阵

| 你的现状 | 建议 | 理由 |
|---|---|---|
| ≤3 人，仍持有包月/按次 coding plan | 维护模式 A | 收益明确，修完 P0 即可继续用；工作量 3-5 天 |
| 已全部转 token plan，只是想要统一入口 | 停维 B，或直接用 LiteLLM/new-api | 自研网关的边际价值低于维护成本；计量/计费/兼容都要重写 |
| 5 人以上小团队，要按人分摊成本 | 转型 C，或买厂商 team plan | 需要补"按 Key 计量 + 单价表 + 预算告警"，否则无法对账 |
| 只是想让 Claude Code 多厂商容灾 | 维护模式 A + 只做 P0-2/5/6/7 | 别做新功能，先把"能用"修好 |

### 5.4 一个务实的判断

- 这个代码库只有约 1 万行后端代码，**维护成本本身不高**；真正的问题是"修不完的正确性债"和"没有测试"。
- 但它的**功能面已经明显落后**于 LiteLLM / new-api / one-api（token 计费、价格表、虚拟 Key、预算、模型映射、协议互转、Prometheus），而这些正是 token 时代的刚需。
- 所以：**留作自用可以，继续当产品迭代不值得。** 如果留下，请把它当"内部工具"而不是"要发布的项目"——这也会让 P0/P1 的取舍简单很多（例如可以直接删掉伪装/时段分流）。

## 6. 如果继续维护：优化与新增路线

### 阶段 0：先让它"能上线"（3-5 人日）

1. 修 P0-1（一行）。
2. 健康检查解密 + 自动恢复 + 开关（P0-2）。
3. 渠道配额周期初始化 + requests/tokens 分开扣（P0-3）。
4. 并发计数改 RAII + 流式生命周期绑定（P0-4）。
5. 错误状态码 + 非流式原样透传（P0-5）。
6. 流式状态判断 + 跨渠道重试 + 失败不扣费（P0-6）。
7. 用 `channel.timeout` 设超时（P0-7）。

### 阶段 1：把"计量"做对（这是 token 时代的地基，5-8 人日）

1. **统一 usage 采集**：
   - OpenAI 非流式读 `usage`；流式注入 `stream_options.include_usage=true`，解析最后一个带 `usage` 的 chunk；
   - Anthropic 读 `message_start.message.usage` 与 `message_delta.usage`，并采集 `cache_creation_input_tokens` / `cache_read_input_tokens`；
   - 流式包装一层 `Stream`，在结束时写日志/扣配额（不再"请求头一返回就扣估算值"）。
2. **价格表** `model_prices(model, input_per_1m, output_per_1m, cache_read_per_1m, cache_write_per_1m, channel_id?)`，按渠道可覆盖。
3. **每请求记录 cost** 与 cache tokens；日志/统计/导出按成本聚合。
4. **预算模型**：把"周期配额（requests/tokens）"升级为"周期预算（金额）"，保留 token 配额兼容；余额/流水表（充值、扣减、退款）。
5. **预算告警**：80%/100% 阈值，Webhook / 邮件 / 企微；管理端红点。
6. **按 Key 统计与限额**：`request_logs` 增加 `user_id`、`key_id`，彻底替代"按 api_key 字符串过滤"；顺带修 P1-4/P1-5。
7. **账单导出**：按月/用户/Key/模型，CSV + 汇总。

### 阶段 2：协议兼容（3-5 人日）

- `/v1/responses`（OpenAI Responses API）、`/v1/messages/count_tokens`（Claude Code 会用）、`/v1/embeddings`（可选）。
- 入站同时接受 `Authorization: Bearer` 与 `x-api-key`；透传 `anthropic-version`、合并 `anthropic-beta`。
- 真正实现 `source_name` 映射（在**每个候选渠道**内改写 `model`，因为同一 proxy 名在不同渠道可能映射到不同源名）。
- OpenAI ↔ Anthropic 协议互转（目前只是按路径透传，渠道类型决定鉴权头，跨协议必挂）。
- 错误体按协议返回；`/v1/models` 补 `object: "list"`。
- 透传 query string。

### 阶段 3：可靠性与可观测（2-3 人日）

- 重试分类：429/5xx/超时 → 换渠道；401/403 → 标记渠道异常并告警；4xx 参数错误不重试。
- 健康检查改为真实 `/models` 或轻量对话探测 + 自动恢复 + 冷却期。
- SQLite 开 `WAL` + `busy_timeout`；日志改为有界队列批量写入（现在每请求一次同步 INSERT）。
- 请求 ID 贯穿 tracing 日志；Prometheus 指标（QPS、并发、渠道成功率、TTFT、token/cost）。
- 优雅关闭时等待在途流式请求（当前 `with_graceful_shutdown` 会一直等流结束，需要有上限）。
- 补集成测试：用 `wiremock`/`axum` mock 上游，覆盖"流式 usage""配额复位""健康检查""错误码""模型映射"。

### 阶段 4：产品化功能（只有确定转型 C 才做）

- 按价格选渠道（最便宜可用渠道）、渠道成本对比。
- 缓存命中率与"缓存节省金额"统计（token 时代很直观）。
- 团队/项目维度（若从个人工具转向小团队）。
- 工作日/夜间不同预算、定时配额。
- 配置导入导出（迁移/备份）。
- 多实例 + Postgres（只有用户数增长才需要）。

### 建议砍掉的功能

- **App Profile 伪装 + 分时段流量方案**：token 时代收益趋零、合规风险高、维护面大。保留"自定义请求头"即可。
- **渠道并发队列**：当前实现既不限制流式并发，又引入 5×2s 的额外延迟（`proxy_routes.rs:211-231`）。要么做对（把 permit 绑到 body 生命周期），要么删掉。
- **`rate_limit_configs` 表**：如果短期不打算执行它，不如从 UI 和路由里移除，避免"配了但没用"的误导。
